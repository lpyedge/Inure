# DOM 鏡像 Spike 報告（2026-11-19）

LIU 2026-11-19 點選「先做 DOM 鏡像 spike，數據說話再定序」。
本報告用真實頁面量三件事：全量快照的體積與採集耗時、突變流
密度、鏡像保真度。量測環境：ovhca、Playwright Chromium、
視口 1280×800。試驗腳本在本機 `~/workspace/domspike/`。

| 頁面 | 類型 | 元素數 | canvas | iframe | shadow | 圖片 |
|---|---|---|---|---|---|---|
| en.wikipedia.org/wiki/WebRTC | 文檔 | 2919 | 0 | 0 | 0 | 7 |

## 快照體積與採集耗時（CDP DOMSnapshot）

| 頁面 | 結構 only | +計算樣式白名單（43 項） | 採集耗時 |
|---|---|---|---|
| Wikipedia | 707 KB / gzip 144 KB | 1199 KB / gzip **165 KB** | 41–100 ms |
| 登入表單 | 9 KB / 3 KB | 26 KB / **4.6 KB** | 1–3 ms |
| 表格 | 23 KB / 5.7 KB | 63 KB / **7.9 KB** | 3–6 ms |
| OSM 地圖 | 65 KB / 17 KB | 114 KB / **20 KB** | 6–13 ms |
| anim | 1.9 KB / 0.9 KB | 2.9 KB / **1.1 KB** | 1 ms |

CSS 文本是獨立的一筆：各站 210–470 KB（框架 CSS），
**按站發一次、哈希引用，不得隨快照重發**（v0 鏡像每份都
內聯全量 CSS，是體積虛高的主因）。

對照視頻基線（本項目先前實測）：WS JPEG 幀 30–100 KB、
10fps 即持續 300 KB–1 MB/s；HLS 配置 1.5–2.5 Mbps 恆定；
RTC H.264 在 anim 頁約 371 kbps（≈46 KB/s）。DOM 快照
（重同步成本）最大的一份（Wikipedia 165 KB gzip）只相當於
2–5 個 JPEG 幀，採集最慢 100 ms。

## 突變流密度（MutationObserver，8 秒窗口）

| 場景 | 結果 |
|---|---|
| 全部真實頁面 idle | **0 ops/s，0 KB/s** |
| Wikipedia 滾動 | 4.5 ops/s，≈0.1 KB/s |
| OSM 滾動（滾輪） | 0（Leaflet 用 transform，不觸發突變） |
| anim 頁（計數器 5 次/秒） | 5 ops/s，≈0.1 KB/s |
| 表單打字 | **0——盲區，見下** |

盲區（MutationObserver 天生看不見，差分通道須另設旁路，
rrweb 同款處理）：表單輸入值（value 是屬性不是突變）、
勾選/選中狀態、滾動位置、canvas 內容、caret/焦點。
這些都有對應的事件流（input/scroll/selectionchange），
屬已知有界的補充，不是未知風險。

穩態結論：真實頁面靜止時 DOM 通道流量為零；同頁面視頻
通道是持續流量。動態頁（anim）DOM 差分 ≈0.1 KB/s 對
H.264 ≈46 KB/s，差約兩個數量級。

## 鏡像保真度（截圖像素差，閾值法，越低越好）

兩代序列化器對照——這是本 spike 最重要的發現：

| 頁面 | v0：DOMSnapshot 重構 | v1：頁內序列化（克隆 DOM+樣式內聯+base） |
|---|---|---|
| Wikipedia | 7.6% | **0.1%** |
| heroku 表格 | 68.9% | **5.6%** |
| OSM 地圖 | 81.5% | **19.4%** |

v0 的損失主要是工程細節，不是結構極限：DOMSnapshot
重構丟結構、缺 `<base>` 使相對路徑資源/字體失效、資源
加載時機。換頁內序列化器（rrweb 路線）後文檔頁近乎逐
像素一致、表格頁 5.6%。

OSM 殘差 19.4% 的構成（目視對照原圖/鏡像圖確認）：
地圖瓦片與標註本身近乎完美；丟的是 **JS 運行時定位的
覆蓋層**——左側歡迎面板/搜索框、右側控制列在靜態克隆
里缺失，容器隨之變寬。這類覆蓋層的樣式由 JS 實時計算，
一次性靜態快照抓不全；**活同步（差分流持續運行）能否
補上，是下一階段原型要驗證的第一問題**，本 spike 不
下結論。

結構性缺口（與序列化器無關，設計上走混合分層）：
`<canvas>`/WebGL 在 DOM 裡無表示（本輪試驗頁恰好 0 個，
結論來自原理而非實測）→ 按幾何位置嵌視頻子流；
跨域 iframe、closed shadow DOM 同理降級處理。

## 結論與定序建議

1. **DOM 主路成立**（文檔/表單/後台類——遠程控制的主要
   目標）：保真 0.1–5.6%、穩態帶寬低視頻兩個數量級、
   重同步便宜（≤165 KB、≤100 ms）。
2. 架構形態：人通道改**混合分層**——DOM 鏡像主路
   （頁內序列化器 + 突變差分 + 表單/滾動旁路事件，
   可靠有序通道傳輸，序號+校驗和+快照重同步）；
   canvas/video 區域嵌視頻子流（復用現有 RTC/WS 管線）；
   突變率爆炸或鏡像置信度不足時整頁降級視頻檔。
3. 序列化器選型已被數據定版：**頁內序列化**，不是
   DOMSnapshot 重構。
4. 建議下一步立項 Phase 2（DOM 通道原型）：序列化器、
   差分協議、觀看端鏡像渲染器、輸入轉發復用現有通道；
   原型第一驗收點就是 OSM 式覆蓋層在活同步下的保真度。

## 未測/邊界

- 本輪頁面無 canvas/WebGL/跨域 iframe/closed shadow，
  這四類的降級路徑只有設計、沒有實測數據。
- 像素差是首屏截圖口徑；滾動後內容、長頁面未測。
- 鏡像在觀看端的輸入命中對齊（點鏡像→真頁面執行）
  未測——輸入仍走現有坐標轉發，命中精度依賴鏡像幾何
  與真頁面一致，這正是保真度數字的意義。
