# 03 关键技术难点与解决

> 本文只收**对设计有决定性影响**的难点，按主题分组，每条给「问题 → 根因 → 方案 → 教训」。
> 故障记录与探针方法见 [PITFALLS.md](PITFALLS.md)，`P19` 对应其中第 19 条。

## 一、让 AI「看得准、点得对」

### 1. 页面在变，动作怎么不点错？——陈旧校验与单元素快速复核

- **问题**：AI 拿到快照到真正点击之间，页面可能已经变了；点错一个「删除」按钮代价很大。
- **方案**：动作必须带观察时的帧号。请求帧等于最新存储帧时，先做**单元素快速复核**（只取目标的 AX 节点、DOM 属性与位置，约 4 次 CDP，与存储帧比对）；任何不一致、出错、不适用一律退回整页快照，由 `check_element_target` 裁决。快路径**只确认、不裁决**，所以它自己永远不会产生误拒。
- **效果**（debug 构建、本地回环、n=20，2026-11-21 实测）：小页点击 `act` p50 130ms → 66ms；大页（约 550 元素）246ms → 68ms。
- **教训**：校验的快路径只允许「放行确认」，绝不允许「自己判拒绝」，否则优化会引入新的误判面。

### 2. 「没收到通知」不等于「页面没变」——变化检测

- **问题**：想让 `observe(since_frame)` 在页面没变时不重新采集。但滚动、CSS 动画、`:hover` 显隐都不产生任何 DOM 事件；`Accessibility.nodesUpdated` 在 Chromium 156 下**从不触发**。
- **方案**：每次观察重新采集候选，核对标签页、主文档和视口后，比较相容的已输出观察。视图相同就回空增量，基帧不相容或无法重建则回整帧。CDP 结构变更日志用于确认文档代次和校验帧能否复用。
- **顺序坑**：日志最初用 `broadcast` 订阅，点击后紧跟的 `observe` 可能赶在订阅任务被调度前判成「没变」。改成 CDP 读泵里的**同步钩子 `tap`**：同一连接上事件总先于其后的响应被读到，先记账后放行响应。
- **教训**：异步订阅者不能当作「先于后续响应」的依据；需要顺序保证就把记账放进读泵。

### 3. 密码不能漏——脱敏要按子树，不能按值

- **问题**：密码框的掩码字符（`••••`）会经**子文本节点**泄漏出来，只替换 `value` 挡不住，掩码长度还等于密码长度。
- **方案**：密码/敏感字段**整棵子树清值、清掩码名**；截图上的敏感区域取自**完整**快照（而不是被裁剪过的响应视图）打黑块；采集期间换页则不交付截图；无法确认敏感区域时拒绝交付截图。
- **同类问题**（2026-11-22）：DOM 镜像通道也曾把密码值原样送给观看端。现在序列化器对 `type=password` 不发 `value` 属性、不发值，`val` 增量与 `value` 属性变化同样不带，非空时只发定长占位。
- **教训**：「输出前脱敏」要覆盖**每一条**把页面数据送出去的路径，新增通道时第一件事是查它会不会带出表单值。

### 4. 跨进程 iframe 的坐标

- **问题**：跨源 iframe 在独立渲染进程（OOPIF），元素坐标相对子帧，AI 看到的坐标必须统一。
- **方案**：子帧原点 = 父帧中 iframe 元素的包围盒左上角；逐级累加偏移；动作定位走 `LocateMap`（id → 会话 + backendNodeId），点击时再换算回屏幕坐标。子帧元素暂不走快速复核（需要帧偏移），退回整页快照裁决。

## 二、让「人看得顺」

### 5. 画面发绿——JPEG 解码器的系统性偏差（P2）

- **问题**：解码出的画面大面积绿色伪影，合成测试图却正常。
- **根因**：纯 Rust 的 `zune-jpeg`（`image` crate 默认）解 Chromium screencast 的真实帧，在特定子采样布局下系统性出错。
- **方案**：JPEG 解码**一律走 ffmpeg mjpeg**；用一张真实 screencast 帧做 fixture 回归测试。
- **教训**：图像库用合成图测不出的问题，必须用目标系统的**真实产物**做 fixture。

### 6. 「太卡」——帧率被三层钳住（P27）

先分层实测，不凭感觉：

1. **常量钳**：RTC 节拍被钉在 15fps → 改 30；码率上限 4M → 8M。
2. **帧泵吞吐**：分段计时（release、真实帧）发现 JPEG 编码（纯 Rust）单项 34ms 是最大头 → 改 ffmpeg mjpeg 约 9ms；整泵从约 59ms/帧降到约 14ms/帧；帧泵跟不上时**排水到最新帧**再处理（排队的旧帧只有延迟没有信息）。
3. **测试素材陷阱**：测帧率的样本视频本身就是 15fps，管线修好后复测仍显示 15，一度误判修复无效。
- 修复后实测：rAF 动画页 30.4fps，60fps 视频 30.3fps，均顶到上限。
- **教训**：测帧率先 `ffprobe` 素材；卡顿要分层（截屏、解码、合成、编码、传输、渲染）逐层量。

### 7. 视口横跳追进编码器（P43）

- **问题**：窗口拖动期间每个中间尺寸都报给边缘，远端视口、截帧、编码器逐个跟着翻动，编码器在两个尺寸间反复重建。
- **方案**：**跟随型尺寸链每一级都要有阻尼**。观看端首报立即、其后 900ms 安定滞后才再发；帧泵分类前先对照当前视口，帧尺寸恰等于视口就按新尺寸重定基准。
- **教训**：只在链路中间一级打补丁，瞬态会从另一级漏进来。

### 8. DOM 镜像的坐标——先问布局是否同构（P41）

- **问题**：DOM 模式点进度条，位置恒偏左 100–150px。
- **根因**：镜像按舞台宽度排版（1500），远端按视口宽度排版（1875）。两边响应式断点不同，且序列化把远端布局的固定像素尺寸冻进了行内样式，两套布局本身就不一致，任何换算公式都救不了。
- **方案**：镜像 iframe 的布局视口钉成快照里的**远端视口**，再整体 CSS `transform` 等比缩放进舞台。布局同构后坐标天然合一，只剩均匀缩放。
- **教训**：镜像的坐标问题，先问布局是否同构，再问换算公式。

### 9. DOM 增量静默死亡（P19，最隐蔽的一坑）

- **现象**：快照正常、点击能转发，但页面变化永远不再同步；新开会话又好了。
- **根因**（三处叠加）：① 观看端断线不发 `dom-stop`，订阅计数只增不减，后来者被当成「后来者」只补快照；② 页面导航后新序列化器无人启动观察者；③ 观看端轮询逻辑在 AV 到达时误杀 DOM。
- **方案**：每次 `dom-start` 一律重新 setup + 快照；WS 断线时若占着名额则补一次释放；计数钳制下限 0；DOM 期间轮询不抢占。
- **教训**：订阅计数要有**连接断开时的统一释放**；「状态由事件补丁维护」的设计迟早漏一条路径。

## 三、传输与媒体

### 10. WebRTC（str0m）的三条硬事实（P23）

1. 会话的 UDP 必须绑在**通告的候选地址**上，否则 STUN 被静默丢弃、ICE 永不连通（Phase 1 最大的一坑）。
2. 浏览器 SCTP 单消息上限约 256KB：DOM 快照走数据通道必须**应用层分片**（16KB）。
3. `Channel::write` 窗满返回 `Ok(false)` 且**不排队**：发送侧要自备待发队列，排空重试。

另（P1）：RTC 恒黑屏的根因是观看端 `ontrack` 把视频流整体赋给 `<video>` 后，随后到达的音频流又整体覆盖了一次。教训：集成测试里没有 RTC 画面断言，黑屏才会漏网。

### 11. 音频：进虚拟声卡，不依赖物理声卡

- 方案：对提供 HTTP 服务且由边缘自拉的 Chromium，进程启动私有 PulseAudio daemon、每进程 socket 与 `null sink`（`rigsink`），Chromium 启动前注入 `PULSE_SINK=rigsink`；合流管线从 `rigsink.monitor` 进程内采集。挂靠 Chromium、纯 stdio 不启动 daemon。
- 细节坑：pulse 流与解码帧的声道布局为空（mask=0）时要按声道数归一化，否则重采样器逐帧拒收；平面声道数据要用 `plane::<f32>()` 读写；AAC 固定 1024 样本/帧手动累积；音视频共用时间原点，否则首段对位的是页面发声前的静音。
- PulseAudio 不存在或私有 daemon/socket 初始化失败时只禁用音频，视频继续可用。`audio_available` 表示启动时 PulseAudio 是否就绪；它不是对后续播放或音量的保证。

### 12. 进程内编码：硬编协商必须一路试到「编码器真能打开」

- 候选序 NVENC → QSV → VAAPI → Vulkan。实测 Vulkan 软渲染能建设备上下文，但没有 encode queue 扩展、编码器打不开。所以**协商不能停在「设备建成」，必须试到 open 成功**，全失败回落 libx264/libx265。
- 这样同一份代码不以任何开发机有无 GPU 为设计基准。

## 四、状态与并发

### 13. 强制接管与取消代次（`exec.rs`）

- **问题**：人接管时，在途的 AI 动作必须立刻停；接管后旧任务不得「复活」；人也不能被「正好此时成功返回的旧 observe」意外解锁。
- **方案**：取消代次（每个 call 开始时领取，接管使之递增）+ 接管闩锁（只有接管之后**新开始**的 observe 才能解闩）。关闭 AI 通道复用同一机制。多步动作在每个副作用前检查（`Select`、`Upload` 写入前同样）。
- **并发缺陷**（2026-11-22 修复）：保持窗原先用「call 开始时的代次」判断自己是否被取代，若先开始的 call 最后结束，保持窗永远失效，人侧输入被一直遮蔽。改为「在途数归零那一刻领取序号」。反序完成测试先复现后修复。

### 14. 持久化不只是给对目录（P35）

- **现象**：加了 `--profile-dir` 后，写入 Cookie/LocalStorage、2 秒后 SIGKILL、同目录重启——Cookie 与 LocalStorage 全丢，IndexedDB 幸免。
- **根因**：这几类存储都是**异步批量落盘**，几秒内被强杀就随进程蒸发；旧的退出路径只硬杀、SIGTERM 根本没接。
- **方案**：SIGINT/SIGTERM（HTTP 与 stdio 两模式）走优雅退出，先发 `Browser.close` 让 Chromium 落盘，超时才硬杀。部署停机用 TERM 不用 KILL。
- **教训**：「写后即杀验恢复」类测试失败时，先分清是没写对地方、没等到落盘、还是停机方式丢了未落盘数据——三者修法完全不同。

### 15. CDP 里「不给参数」不等于「给默认值」（P36）

- `Input.dispatchMouseEvent` 的 `mousePressed` 缺省 `clickCount` 时，页面根本收不到 mousedown。Puppeteer/Playwright 永远显式带，所以常规工具链遇不到。
- 方案：缺省由边缘补 1。教训：改任何注入参数的缺省行为，先把「不给 / 给 1 / 给 N」三档在目标浏览器上实测一遍。

## 五、鉴权（2026-11-22 重做）

### 16. 浏览器 WebSocket 和 `<video>` 都带不了请求头

- **约束**：想做到「令牌只走请求头/body，不进 URL」，但浏览器 `new WebSocket()` 不能设头，原生 `<video src>` 也不能；iframe 内嵌时第三方 cookie 又会被拦。
- **方案**：统一成「启动令牌 → `POST /session`（body）→ 内存票据」。普通请求走 `Authorization: Bearer <access>`；WebSocket 连上后 3 秒内首帧认证；HLS 用登录后才下发的**只读路径钥匙** `/stream/{key}/…`（播放列表里的相对分片地址自然继承前缀），它不具备任何控制能力。
- **旧做法的问题**：此前把**主令牌**改写进播放列表 URL，是更大的泄露面。
- **教训**：每加一类子资源（script/css/img/media/worker），都要按「它拿不到页面凭证」重新检查鉴权（P32 的同类坑）；带令牌的部署形态必须有一条真浏览器端到端探针。

### 17. 无时限 refresh 的风险控制

- refresh 无时限（用户明确选择，体验优先），所以**每次使用即轮换**：旧的立即作废，被盗用时真假双方必有一方失效而可被察觉。票据只存内存，进程重启即全部失效，不需要吊销接口。

## 六、测试方法论（栽过的跟头，详见 PITFALLS §六）

- **探针先自证**：夹具必须在源头产生可测信号，测量点也要用已知有信号的输入校准过。曾因测试页的音轨本身没声音，险些得出「Chromium 不解码音频」的错误结论并展开三条无谓的改造线（P44）。
- **点击成败以远端状态为证**（`activeElement`、计数器），不看坐标自洽。
- **隔离归因三件套**：CDP 直打（远端能力）→ 原始 WS 往返（边缘协议）→ 观看端真实手势（全链路），逐层定位，不要跨层猜。
- **探针原点要与用户实测一致**：局域网 IP 不是安全上下文，127.0.0.1 会让剪贴板类测试假通过。
- **清进程别用 `pkill -f`/`pgrep -f` 配合含目标名的命令**：模式串会匹配到执行它的 shell 自己（退出码 144）。用 `$!` 记录进程号，或让包装脚本 `exec` 目标命令。本项目开发中这个坑踩了不止一次。
- **每次验证后检查 `/tmp`**：一次性目录泄漏要靠测试后的目录计数发现，而不是靠想。
