## 0. 背景速覽

- 項目：RIG — Remote Interaction Gateway 的 Chromium 控制端。Rust 邊緣程序
`rig-edge-browser` 拉起本機 Chromium（CDP 控制），向觀看頁提供三種呈現：
WebRTC 視頻+音頻（主路）、DOM 鏡像（頁面序列化重播，低帶寬）、HLS（兜底）。
- 畫面來源：CDP screencast（JPEG 幀）→ 邊緣幀泵分類/合成 → RTC 編碼（libx264）
或 WS 幀流。音頻：Chromium 聲音進 PulseAudio 虛擬聲卡 `rigsink` → 兩路採集
（RTC Opus / HLS AAC）。
- 關鍵文件：
- `crates/rig-edge-browser/src/human.rs` — 幀泵（幀分類、內容幀貼圖、合成）
- `crates/rig-edge-browser/src/viewer.js` / `viewer.html` — 觀看頁（狀態機在這裡）
- `crates/rig-edge-browser/src/rtc.rs` — WebRTC（str0m）會話與音視頻 feeder
- `crates/rig-edge-browser/src/media.rs` — HLS 管線與 pulse 採集
- `crates/rig-edge-browser/src/dom.rs` — DOM 序列化/鏡像
- `crates/rig-edge-browser/src/main.rs` — HTTP 路由、/channels 通道開關
- `docs/EDGE_BROWSER.md` — 設計與全部決策記錄；`docs/PITFALLS.md` — 45 條踩坑實錄
- 實測環境：邊緣跑在 Linux 伺服器（Chromium 1255 全量構建，headless），
用戶以 Windows Edge 經局域網開觀看頁，看 Bilibili 視頻頁。設備縮放 DSF 恒 1。

## 1. 主要問題 P1：視頻模式畫面仍會亂跳（未根除）

### 現象
用戶原話：「視頻模式下還是會亂跳，改成固定尺寸只是能減少發生的概率。」
即：分辨率設「跟隨窗口」時跳得頻繁；設固定 1280×800 後變少但仍有。

### 已排除/已修的部分
- 尺寸鏈：跟隨模式下觀看頁窗口尺寸的瞬態值曾被逐個報給邊緣，
遠端視口與 RTC 編碼器跟著反覆重建（生產一晚 468 次）。已加 900ms 安定
滯後（viewer.js `reportSize`），固定模式下編碼器全會話僅 2 次重建
（含啟動 1 次）——**固定模式下仍跳，與編碼器/尺寸鏈無關**。
- screencast 幀二象性：Chromium 在視頻播放頁交替發「整頁幀」與
「只有 video 元素畫面的幀」（尺寸即元素尺寸、無標誌位）。幀泵現按
「見過的最大整頁尺寸」分類：整頁幀透傳並歸一化；內容幀解碼後按
video/canvas 的視口矩形貼回最近整頁 RGB（human.rs 幀泵段）。

### 最新證據（2026-11-20 晚，新版上線後用戶真實會話的幀泵取樣日誌）
```
[pump] 内容帧 rect 取样 865x487 sf=1 rects=[(295, 172, 865, 487)]
[pump] 内容帧 rect 取样 803x452 sf=1 rects=[(41, 168, 803, 452)]
[pump] 内容帧 rect 取样 803x452 sf=1 rects=[(41, 168, 803, 452)]
[pump] 内容帧 rect 取样 818x460 sf=1 rects=[(34, 168, 818, 460)]
[pump] 内容帧 rect 取样 803x452 sf=1 rects=[(41, 168, 803, 452)]
```
讀數：
- 同一會話內 Bilibili 的 video 元素出現 **3 種幾何**（865×487@(295,172)、
803×452@(41,168)、818×460@(34,168)）——頁面自身在 reflow（播放器佈局
隨 UI 元素出現/消失切換），不是邊緣改的尺寸。
- `sf`（metadata 縮放因子）恒 1——「rect 被 sf 錯縮放」的懷疑**不成立**，
可從分析中劃掉。

### 現行貼圖設計的薄弱點（請重點分析）
1. rect 緩存（`gate_rects`）以內容幀尺寸 `(w,h)` 為鍵，失效條件只有：
頁面滾動、視口重定基準、尺寸鍵不匹配時重取。**元素在無滾動的 reflow
中移動/改尺寸時，緩存不自知**：某尺寸的內容幀再來時會按舊 rect 貼圖，
直到下一次重取才糾正——貼錯位置的幀在用戶眼裡就是「跳」。
2. 即使 rect 完全正確：整頁幀本身也如實帶著 reflow（元素真的移了位），
這部分「跳」是頁面行為的忠實傳輸。但內容幀貼圖與整頁幀到達節奏不同，
兩者交替呈現時，視頻區會在「貼圖位置」與「整頁幀裡的位置」之間來回切，
放大跳動感。是否應在 reflow 頻發頁面降級為「內容幀直接丟棄、只用
整頁幀」，或給 rect 緩存加短 TTL/每幀校驗，請評估代價與收益。
3. rect 匹配用 ±3px 容差 `find` 第一個近似者；頁面有多個 video/canvas
且尺寸接近時可能貼到錯誤元素（本次日誌只有單元素，未觸發）。

## 2. 主要問題 P2：DOM 模式下沒有聲音

- 現行設計是「影音與 DOM 互斥」：進 DOM 時觀看頁主動關邊緣影音
（viewer.js `domStart` POST /channels {av:false}），理由是當時 vid 元素
同時承載 HLS 播放與 RTC 畫面，DOM 顯示期間不應出聲。
- 技術事實：RTC 音頻軌與畫面顯示是解耦的——DOM 期間 RTC 音頻包
照常流到觀看端（約 96kbps），只是 vid 被本地靜音（dbg67/dbg69 探針實測
DOM 期間 audioBytes 持續增長）。即 **RTC 路徑下 DOM 模式完全可以只保留
聲音、關畫面**；HLS 兜底路徑沒有這個條件（音頻封在 HLS 流裡）。
- 待用戶拍板：DOM 模式是否改為保留聲音（低帶寬看 DOM + 聽聲音是合理
場景）。若改，需處理：HLS 路徑的降級口徑、進 DOM 不再關邊緣 AV 後
pollAv 自愈邏輯的簡化、vid 隱藏但不靜音的自動播放策略（Edge/Chrome
對「不可見媒體出聲」無額外限制，但需實測）。

## 3. 已解決（勿重複分析，列出以便對照）

- 無聲問題（視頻模式）兩層定因均已修（PITFALLS §42、§45）：
(a) 觀看頁進 DOM 關影音、退出不恢復 + vid 靜音無收斂點 → 已加
avWasOn/restoreAvAfterDom + showDisplay 靜音收斂；
(b) 邊緣 AV 被關後持久卡死（恢復代碼沒在同一頁面生命週期跑到時
永遠無聲，且觀看頁菜單無 AV 開關、用戶無從恢復）→ pollAv 加兜底
自愈（視頻模式見 av 關且可用即開回），觀看頁資源加 no-store。
用戶已確認視頻模式有聲。
- 音頻鏈本身（源頭解碼→虛擬聲卡→採集→RTC→渲染）經四級電平實測無故障
（PITFALLS §44，含探針夾具污染的教訓）。

## 4. 我懷疑有問題、但未證實的地方

- S1rect 緩存無 TTL：見 P1 第 1 點。這是我對 P1 的首要懷疑。
- S2RTC 會話/want 計數泄漏：/ready 的 sessions 曾見 4（用戶單人
使用）。殭屍會話會讓 feeder 常開（CPU/帶寬浪費），未查來源。
- S3DOM 期間 RTC 音頻無謂推流：觀看端靜音但包照發
（dbg69 phase3 實測流量滿速）。屬浪費，且與「DOM=低帶寬」的賣點矛盾；
與 P2 的拍板聯動（若 DOM 保留聲音則不算問題）。
- S4/channels 的 av 是邊緣全局量：多觀看端並發時，一端進 DOM
會關掉所有人的聲音。當前單人使用口徑下可接受，但狀態模型本身是毛邊。
- S5HLS 兜底路徑未做過與 RTC 同級別的音頻端到端探針（僅集成
測試斷言 HLS 流含 AAC 軌）。pollAv 自愈對 HLS 的實際效果未專門驗證。
- S6可觀測性差：生產日誌被 ffmpeg swscaler 警告刷屏（每幀級），
有效診斷行靠 grep 撈；幀泵此前無任何幀級統計，P1 的取樣日誌是本輪
才加的（只有 rect 重取時才打，貼圖次數/丟棄次數仍無統計）。
- S7觀看頁 /channels 用 2 秒輪詢而非 WS 推送；DOM 鏡像
對真 shadow-DOM 站點無支持（內部頁已用視頻模式繞行）；YouTube 因伺服器
出口 IP 被站點側機器人門檻攔截（與本程序無關，待用戶在持久化 profile
登入後複測）。
