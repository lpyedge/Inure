## 1. 控制权与动作协议（优先级最高）

### C01 人工接管闩锁 TOCTOU 竞态（P0）

**证据**：`crates/rig-edge-browser/src/exec.rs:115-120` 先获取 Mutex 读取 `latched`，释放锁之后再 `await begin_inner()` 获取第二次锁并增加 `active`；`exec.rs:152-158` 接管将 `cancel_epoch` 递增并置 `latched=true`。

**最小交错**：`act` 第一次锁看到 `latched=false` → 接管设置 `latched=true, epoch=1` → 先前 `act` 第二次锁 `begin_inner()` 领取 epoch=1 → 执行过程的 epoch 校验认为未取消，可能执行副作用。即违背“接管后直到重新 observe，新的 act 全拒绝”的已批准契约。

**最小修复**：单次 Mutex 临界区内完成 `latched` 检查、`active += 1`、`generation += 1`、句柄 epoch 分配；不要在检查与开始之间 `await`。添加可控调度的竞态测试：接管插入检查与开始的边界时 act 必须拒绝。

### C02 旧 observe 可错误解除接管闩锁（P0）

**证据**：`ai.rs:155-165` 在 `begin_observe()` 领取 handle 后，若 `observe_req_inner` 成功，无条件调用 `note_observed()`；`exec.rs:145-148` 无条件清 `latched`，没有检查 observe 领取的 epoch 是否早于人工接管。

**最小交错**：observe 先开始 → 用户接管 → 旧 observe 成功返回 → 闩锁被清除 → 新 act 放行。用户要求的是“接管后的**新**观察重新同步”，旧观察不能满足。

**最小修复**：`note_observed(&ExecHandle)` 在同一锁下验证 `h.epoch == current_cancel_epoch` 且观察在最新接管之后开始；旧代次绝不解锁。补 `observe before takeover / takeover / old observe success / act must abort` 测试。若观察因重定向过渡导致快照过期，也不得误解除闩锁。

### A01 动作完成帧号可能与有效快照不一致（P1）

**证据**：`ai.rs:98-109` 帧号在执行 `build_observation` **之前**递增；`ai.rs:449-453` 忽略 `observe_full()` 的 `Result`，直接返回 `ActionResult::Done {frame_id:self.frame.load(...)}`。并发其他 observe 也可更改全局帧计数。

**影响**：返回的 `frame_id` 可能根本没有对应成功构建/提交的观察；调用方据此做下一次 act 时遇到 StaleFrame，且“Done 附带新帧”的契约失真。

**修法**：返回本次 `observe_full()` 成功得到的 `obs.frame_id`（且说明该帧已成功提交还是仅返回局部快照）。刷新失败时动作副作用已执行，不能简单伪装成 Rejected；使用明确的“动作已执行、结果观察失败/需重新 observe”的结果语义，必要协议变更先取得批准。

### A02 `active` 非 RAII / 取消安全（P1）

**证据**：`exec.rs:99-105,122-143` 自行增减 `active`；`ai.rs:155-165,265-277` 依赖正常执行路径到达 `end()`。异步任务被取消或 panic 时不能保证 `end()` 运行。此前整改文档称“RAII 句柄”，但 `ExecHandle` 为 `Copy` 且没有 `Drop`，只是手动配对。

**影响**：`/health.exec_in_flight` 虚高，执行状态保持窗不回 Idle，Viewer 可能长期遮蔽输入。**建议**将在途计数变为可 Drop 的 owned guard（同步原子计数或显式独立生命周期对象），并对 `tokio::spawn(...).abort()` 做回归。

### 业务协议补充

`ai.rs:283-287` 当前幂等键为 `request_id + frame_id + action JSON`，允许同一 request_id 承载不同动作。这是此前因测试客户端复用 id 而特意接受的方案，**不是本次新增缺陷**；但不等价于“同 id 必须幂等”，未来接入第三方客户端时建议在 API 文档中明确。

## 2. RTC 视频跳动根因与最小修复

### V01 reflow 时 rect 缓存失效条件不充分（P1）

`human.rs:409-418` 的 `gate_rects` 与 `gate_rects_for` 未记录采样代次或 TTL；`human.rs:569-615` 只要本次内容帧 `(w,h)` 与缓存 key 一致，就直接命中旧 rect。位置变化但视频区域尺寸不变时没有再次执行 `getBoundingClientRect()`；生产样本中同一会话多个几何变化已证实页面在 reflow。**sf=1 的生产证据不支持“缩放因子算错”作为该次故障原因**。

**快速实验**：在同一 Bilibili 播放场景、固定 1280×800，运行两种策略 A/B：A. 丢弃内容帧只发布整页帧；B. 当前贴图。记录视频画面跳动、有效 FPS、全页/内容帧比例。若 A 消除“额外跳”而视频 FPS 下降，可证明贴图链是关键放大因素，不把 A 无条件作为最终策略。

**缓解**：在内容帧尺寸再现时检查最新几何；以 200–500ms TTL 作应急措施，同时给 DOM Layout/ResizeObserver（含 rect、滚动、viewport）设计可主动失效的版本号。TTL 本身无法保证在 reflow 立即发生的 200ms 内正确。

### V02 合成底图不是干净的整页基准（P1）

`human.rs:616-646` 每次 `let mut canvas = (*base).clone()`，而 `base` 就是 `last_rgb`；先前内容帧贴上去后会把同一个 `last_rgb` 改为合成结果。因此视频从位置 A 移到 B 时，新视频贴在 B，旧位置 A 的像素仍留在上一轮合成画面内，直到新的真正整页帧覆盖。**这不是单靠缩短 rect TTL 就能解决的。**

**修法**：分别维护 `full_base_rgb`（最后一次真实整页帧，只能由整页更新）与 `display_rgb`（该轮完整合成输出）；在新鲜整页底图上贴图，而不是在上次 display 结果上叠加。若 rect 变动而 full_base 过旧，应等待新基准或短时回退全页帧，不能盲目重复覆盖。

### V03/V04 尺寸启发式及多 video/canvas 匹配（P2）

`human.rs:529-530` 的 90% 阈值没有画面类别的显式 CDP 标志；当播放器接近全屏或真实视口尺寸变化时可能误分类。`human.rs:657-658,698-708` 采用历史最大面积作为基准，并将后续不同宽高的整页图直接 resize 到基准，可能引入比例变形或“呼吸感”；`human.rs:569-579,607-613` 采用 ±3px 找第一个视频或 canvas，在多个相近尺寸元素场景缺乏身份对应。

**建议**：建立 `viewport_epoch`、`full_frame_epoch`、`rect_geometry_epoch` 三组可诊断元数据，并明确“rect 与内容帧身份无法可靠对应时直接丢弃内容帧”；归一化尽量使用裁切/补边而不是无条件横纵拉伸，需检查输入 CDP metadata 的坐标口径。大幅改变采集方式（例如整页 captureScreenshot）需要先做 CPU/延迟对照，不建议未经基准就替换主链路。

## 3. DOM 生命周期和 RTC 数据通道

### D01 重复 `dom-start` 导致订阅计数泄漏（P1）

`viewer.js:1355` WebSocket 建立就发一次 `dom-start`（用于自动检测），之后 `viewer.js:702-716` 见表单快照又执行 `domStart(true)`，在 `viewer.js:758` **再次**发 `dom-start`。服务器 `main.rs:1040-1043` 即便 `dom_active` 已为 true 也无条件调用 `viewer_start()`；`dom.rs:448-453` 每调用一次就 `fetch_add(1)`。连接只关闭一次（`main.rs:1068-1070`），所以一个观看端可能使 `viewers` 余额永远为 1；`/ws?dom=1` 同样可能重复进入。

**修法**：服务器端每个 WS 连接做幂等状态迁移 `false → true` 才加订阅，`true → false` 才减；客户端分别维护“后台 DOM 感知连接”与“前台 DOM 显示”，两者共用一份订阅，不重复发 START。必要时将 DOM 订阅封装为 owned guard。测试 `start,start,stop,close`、`start,close` 以及自动快照切换，最终 count 必须为 0。

### D02 WS 发送侧先退出会跳过接收侧清理（P1）

`main.rs:1065-1074` 的清理（DOM 退订、JPEG 需求减一）位于 `recv_task` 的函数末尾；`main.rs:1076-1078` 若发送任务先结束则直接 `recv_task.abort()`，清理代码不会得到执行。`dom_active` 的 Boolean 本身也不是实际订阅数，不能靠一个布尔做次数补偿。

**修法**：将连接资源声明为连接拥有的 guard，`tokio::select!` 结束后由唯一父作用域释放；不要把重要清理放在可能被 abort 的子任务末尾。再测远端只关闭接收侧、发送失败、突发断网、刷新、浏览器崩溃。

### T01 RTC `dc_pending` 无界队列（P1）

`rtc.rs:588` `VecDeque<String>` 没有总字节/条数上限，`rtc.rs:665-672` 每个 DOM 消息都展开成分片加入；当 `rtc.channel.write` 因 SCTP 窗口满返回 `Ok(false)`，`rtc.rs:746-760` 只能等待再发，生产速度大于消费速度时会无限积累。项目不变量明确要求数据路径有界。

**修法**：对每个 RTC 会话设置总字节硬上限、最大未完成分片数、队列驻留时间；超限时应**废弃整个旧快照/旧增量代次并请求 resync**，不能丢单个片段却让后续 seq 继续前进。引入 `pending_bytes` 与 `queue_age` 指标，并在 SCTP 慢消费者压测中验证 RSS 平稳。

### D03 Viewer 分片重组同样缺上限（P2）

`viewer.js:93-103` 的 `chunkBuf` 会对任意 `m.n` 构造 `new Array(m.n)`；残缺包没有过期回收，也不在 RTC 会话换代时 `clear()`。应校验分片序号、数量、总字节，给 5–10 秒的最大片段生命周期与全局容量限制，超限请求全量快照。不要用“只要收到可靠有序 DC 就必然没有缺包”替代跨会话/关闭场景的处理。

### D04 Region 双端缓存跨页面存活（P2）

`dom.rs:523-535,605-650` 的 `state: HashMap<id,(signature,time)>` 随区域/页面变更不清理；`viewer.js:845,869-870` 的 `regionCache` 同样跨快照永久保留。页内序列化器 `dom.rs:19-28` 每个新文档的 id 从 1 重新分配，可能把旧页面相同 id 的截图暂时贴给新文档，也会导致驻留图像增长。

**修法**：Region 缓存 key 使用 `(session/page_epoch, region_id)`；导航时清空上一代；扫描时淘汰已消失的 id。为客户端加 `max_entries/max_bytes`，保留“同一代快照重建复用上一张图”的既有优化。

## 4. 音视频资源、业务逻辑与降级

### M01 实际上不是“RTC 主路、HLS 按需启动”（P1）

`main.rs:656-669` 收到 `/channels {av:true}` 就直接 `app.media.start()`；`media.rs:293-340,394-428` 的 HLS 管线同一帧分别编码 HEVC 与 H.264。`viewer.js:559-575` 正常 RTC 已连通时选择 RTC 展示，但并没有因为已进入 RTC 而停止 HLS 管线；`rtc.rs:195-300` 还有独立的 RTC H.264 feeder。故有 AV 的常规 RTC 会话**可能并行运行三路视频编码**，还有 RTC Opus/HLS AAC 两套音频采集/编码。此路径由代码确定，实际耗费需测量，不能预填百分比。

**建议**：把 `av_enabled`（用户是否需要声音）与 `hls_pipeline_running`（兜底编码器是否实际需要）分离。RTC healthy 时默认 HLS 不运行；RTC 在超时或失败后再按需启动 HLS；HLS 可按客户端 codec 能力只启动一个 rendition。切换时利用短暂 grace 避免频繁起停。对应性能测试需记录 RTC/HLS 线程 CPU、RSS、编码 FPS、首次出画时延以及回退耗时。

### M02 HLS 音频线程缺少统一 stop（P1）

`media.rs:361-380` 创建的 `rig-media-audio` 线程只 `.spawn(...).ok()`，没有保存句柄；其 `audio_main()` 在 `media.rs:575-640` 采集循环中只在 `go` 为真之后发送编码 packet，且仅在发送发生时才能发现接收端 Disconnected。如果 HLS 在第一张有效 RGB/合流器建立**之前**停止，`go` 一直 false，音频线程可能无限监听 PulseAudio 而不退出。反复快速启停可能积累辅助线程和音频设备句柄。

**修法**：为音频线程传入同一个 `stop`，持有 join handle，在启动失败/停止/降级等所有路径显式终止与回收；考虑 Pulse 阻塞读需要可中断手段。测试 `start → 100ms stop`、无视频帧/无声卡、10 次启停，检查线程数与 Pulse 客户端数。

### M03 HLS 启动错误未被渠道响应体现（P2）

`main.rs:661-669` 对 `app.media.start().await` 使用 `let _ = ...`；用户拿到的仍是普通 ChannelState，不知道是缺声卡、编码器初始化失败还是关闭状态。建议返回 `configured/running/starting/failed` 及脱敏的 `last_error`，并在 `/health` 暴露可诊断失败状态。已有 human 通道实施过错误反馈，应保持一致。

### U01 DOM 声音（业务待决，不是既有故障回归）

`viewer.js:738-752,478-485` 明确在 DOM 显示时关全局 `av` 并对 `vid` 静音；RTC `rtc.rs:649-657` 在会话连通时仍写 Opus 音轨。用户提供的探针显示音频已经抵达 Viewer。因此 DOM 静音是**UI/资源策略**而非“无法经 RTC 送声”的技术限制。

建议将其作为产品选项定版：默认“DOM 可保留 RTC 声音”更符合轻量显示+听课/视频的场景。实现须让 `audioWanted` 与 `videoWanted` 独立、避免后台无效 H.264 编码；Edge 自动播放策略需要真实测试。HLS-only 时可明确显示“DOM 音频不可用/切视频播放”或设计独立音频播放方案，不能假装已有 RTC 能力适用于 HLS。

### U02 全局 AV 与多 Viewer（已知边界）

`main.rs:656-669` 是进程全局的 HLS AV 状态，`viewer.js` 某观看端 `domStart` 关闭会影响其他端。当前业务已批准**单人受信工具**，不应将其当成当前 P0 多租户缺陷；但应在 README 里标注“并发 Viewer 不保证相互独立”。未来多用户成为需求时将 global media policy 与 per-client desired mode 分离，再加唯一控制权/Lease。

### U03 自适应模式切换缺少迟滞（P2）

`viewer.js:687-716` 依据单次快照的 video 面积与“interactive < 3”等阈值决定视频/DOM，不区分主要播放器区域和页面导航控件。Bilibili 等视频页若含较多按钮，可能被误选为 DOM；动态网页比例临界变化时缺少连续判定/最小停留时间，反复切换可能伴随 AV 开关。建议基于主视频面积、动态区域帧率和 2–3 次连续稳定判断；将手动锁定作为最高优先级。**此前 dbg35 的单场景通过不等于所有视频网站均正确。**

## 5. 观测、安全边界和整体架构

### O01 关键指标仍缺席（P2）

现有 `/health` 的 frames/latency 能说明基本运行，却无法辨别每张帧是“全页/内容/缓存命中/丢弃/贴图”，也没有 `dom_viewer_count`、`rtc_active_session_count`、`rtc_want`、`dc_pending_bytes`、`region_cache_bytes`、`audio_rms`。建议对 `[pump]` 改为**定期汇总计数**而非每帧刷文本；FFmpeg swscaler 同类消息限频输出，保留第一条与累计条数。目标是用一次会话的 30 秒指标判断跳动发生在哪个阶段。

### 需要纠正的一处问题清单推论

`main.rs:599-612` 的 `/ready.sessions` 是 `app.browser.sessions.lock().await.len()`，即 CDP 会话数，**不是 WebRTC Viewer 数量**。单个用户见到 4 不足以证明 RTC session/want 泄漏。RTC 会话是否泄漏应另加 `rtc_active_sessions` 与 `want` 指标，再看断开后能否回到 0；`rtc.rs:89-100` 本身已经有 `WantGuard` Drop 配对，不能无证据推翻。

### 安全复核与既定裁定

- 非回环要求 Token + TLS、Viewer iframe `sandbox="allow-same-origin"` 且无 `allow-scripts`、输入内容不作为服务端命令执行等属于正确安全边界，应保留。
- URL `?token` 用于浏览器媒体/WS 已是显式设计，不把它写成未经允许的 P0；但存在访问日志、浏览器历史等泄漏残余风险。未来需要外部共享时，可引入短寿命 Viewer ticket、受限 Cookie、父页面 `Referrer-Policy: no-referrer`，保留现有直连能力。
- `docs/SECURITY_DESIGN_2026-11-19.md` 中 B1/B2/B3/B5 已由负责人撤销；这次不把目标页隔离、Origin 生命周期、WS Origin 和跨租户 DB 约束作为“必须立即修复”的本阶段工作。
- 预留的正式 Gateway/Connector/CLI 功能还处于 `docs/ROADMAP.md` 的未开始阶段：`rig-connector` 的 Enroll/Run、`rig-cli` 的 Login/Tcp/SshProxy 均明确返回 not implemented；`rig-gateway` 核心路由也在 TODO。**这是已声明的计划范围，而非声称现有 M1 edge 产品缺陷。**避免以“项目整体可商用”向外宣传尚未实现的远程穿透能力。

### 架构优化（不建议大规模重写）

1. **明确三个状态所有者**：`ViewerConnection` 只管 per-WS 订阅/显示策略和 RAII 清理；`MediaCoordinator` 只管 RTC/HLS/Audio 按需启动；`ExecControl` 管强制接管 epoch/闩锁与在途计数。主业务已足够复杂，再把状态散落于前端、HTTP 以及 feeder 会增加不可测组合。
2. **拆开“画面模式”和“声音需求”**：`Display = RTC / JPEG / DOM`、`AudioWanted = On/Off`、`MediaSource = RTC / HLS`，全局 `gate_human/gate_ai` 仅表示能力开关，而不是混用实际工作线程状态。保留既有 REST/WS 兼容接口，先做内部语义清晰化。
3. **帧合成模块化且可测试**：从 `human.rs` 抽取纯函数 `classify_frame/validate_rect/compose_with_clean_base`，以录制的元数据和 RGB 小图进行无浏览器单元测试；不必新增微服务或跨进程消息总线。
4. **将严重故障转为自动化回归**：在 edge_it.rs 增加真实用户时序（自动模式、音视频切换、断线），在 exec.rs 加 tokio 竞态测试；保留 11 项已记录通过的现有 IT，不因本轮问题改低断言标准。

### 优先补的 12 条测试

1. `begin_act` 两次锁之间人工 takeover 交错；新 act 不得落副作用。
2. 旧 observe 在 takeover 之后成功；闩锁仍保持到后续新 observe 成功。
3. 正在 observe/act 的 HTTP handler 或 tokio task 被取消；in-flight 正确归零。
4. `observe_full` CDP 错误：返回 `Done.frame_id` 不得指向未构建帧。
5. Viewer `dom-start,dom-start,dom-stop,close`；计数恰好回零。
6. WS 发送侧先收到 socket send error；不遗留 DOM/JPEG 订阅。
7. 背压下 1MB DOM 快照反复推送，RTC DC 队列内存受上限控制。
8. DC 分片中断/关闭/重新建立：客户端 chunkBuf 清理并重新请求快照。
9. 相同视频尺寸但不同 x/y 的 reflow；不准复用旧 rect。
10. A/B 全页帧与内容帧交错；旧视频区域不会保留残影；不同 video 同尺寸不误贴。
11. RTC 已连通、DOM 仅听音、RTC 故障 HLS 接管、HLS 音频可听四条真实渲染路径。
12. HLS 在没有第一张 RGB 时连续启动/停止十次；线程/文件/声卡资源无泄漏。
